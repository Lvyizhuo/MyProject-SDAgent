## 二、链路梳理（实施后）

```
浏览器
  └─ fetch POST /api/chat/stream  (Accept: text/event-stream)
       │  ← SSE: stage / delta / done / error
       ▼
nginx (:5173)  ── proxy_buffering off ──▶  backend (:8080)
                                          │
  ChatController.chatStream ── SseEmitter(180s)
       │
       ├─ 落库：会话 upsert + 用户消息
       ▼
  ChatService.chatStream
       ├─ prepare()  ← 与同步路径共用同一套前置编排
       │    ① facts（Redis）              ② priceEnrich（Redis）
       │    ③ priceCache（Redis）          ④ buildUserMessage
       │    ⑤ clarification（纯规则）       ⑥ fastPath（纯规则）
       │    ⑦ qaCacheLookup（Ollama 嵌入）  ⑧ pricePrefetch（Tavily 后台）
       │    ⑨ planning（规则捷径 / LLM）     ⑩ intentClassify（纯规则）
       │    ⑪ toolExec（Tavily / 补贴计算）   ⑫ buildExecPrompt
       │    → 逐阶段推送 stage 事件
       ▼
  ExecutionFallbackChain.executeStreamWithFallback
       ├─ clientCreate（缓存命中，~1ms）
       ├─ Advisor 链：Security → ChatMemory → ReReading → QuestionAnswerAdvisor(RAG) → Timing → Logging
       │     └─ RAG：缓存 → 语义缓存 → 嵌入 → 向量召回∥关键词召回 → RRF → rerank → 阈值 → parent
       └─ 模型流式输出 ──▶ 逐块 delta 事件
       ▼
  ChatService 组装 references → done 事件（content + references）
```

**同步路径**保持不变（`/api/chat`），与流式路径共用 `prepare()`，仅最后一步执行方式不同。

### Advisor 链顺序（本次显式固定）

此前 `QuestionAnswerAdvisor` 与 `MessageChatMemoryAdvisor` **未设置 order**，实际执行顺序依赖 Spring AI 默认值。
本次显式固定，消除不确定性：

| Advisor | order | 说明 |
|---|---|---|
| SecurityAdvisor | 10 | 词表 + 正则注入检测 |
| MessageChatMemoryAdvisor | 20 | Redis 历史（本次新增显式 order） |
| ReReadingAdvisor | 50 | 提示词改写，不额外调模型 |
| QuestionAnswerAdvisor | 60 | RAG 检索（本次新增显式 order） |
| TimingAdvisor | 85 | 切分 preModel / llmCall |
| LoggingAdvisor | 90 | token 用量与检索结果 |

### P1-1 Rerank 提速（含一个隐性故障修复）

**这一项的关键发现：rerank 此前从未真正生效。**

`DashScopeRerankService.callRerankEndpoint()` 原本用 `.body(Object.class)` 接收响应。
Spring 会选中 `ObjectHttpMessageConverter`，它**只支持 `application/octet-stream`**，
解析 JSON 数组必然抛：

```
Error while extracting response for type [java.lang.Object] and content type [application/octet-stream]
```

该异常被 `rerank()` 的 catch 吞掉 → **每次请求都静默降级为纯向量检索**，日志里只留下一行 WARN。
而客户端 read timeout 恰好是 5s，rerank 服务的 CPU 推理又要 5s+，
于是每次 RAG 都要先白等 5 秒超时、再拿一个解析失败的响应 —— **5 秒纯浪费，零收益**。

这解释了为什么之前所有 RAG 文档的 `score` 都是 `0.0000`。

**修复与提速**

| 措施 | 内容 | 实测 |
|---|---|---|
| 修复响应解析 | `.body(String.class)` + Jackson 按需解析（顶层数组 → `List<Map>`，对象 → `Map`） | rerank 真正生效 |
| 放宽 read timeout | 5s → **30s**（原来推理稍慢即超时降级） | 消除超时降级 |
| 批大小 | rerank 服务 `model.predict(..., batch_size=1)` | 5163ms → 3259ms（**-37%**），打分与排序**完全一致** |
| 候选数 | `candidate-top-k` 20 → 10 → **6** | docs 10→6，totalChars 4200→2000 |
| 单条长度上限 | `rerank-max-doc-chars` 3000 → **800**（真实 chunk 均长 420，最大 768） | 消除长尾拖累 |
| 并行化 | 向量召回 ∥ 关键词召回（独立 4 线程池 `rag-retrieval-*`） | -90ms |
| 嵌入复用 | 查询向量算一次，语义缓存匹配与向量召回共用 | vectorRecall 624ms → 8–14ms |

**RAG 管线耗时对比**

| 阶段 | 优化前 | 优化后 |
|---|---|---|
| rerank | **5 023 ms（85.7%）**（实为超时失败） | **2 153–2 406 ms**（真实推理） |
| embedQuery | —（混在 vectorRecall 里） | 140–229 ms |
| vectorRecall | 624 ms | **8–14 ms** |
| keywordRecall | 87 ms | 18–41 ms |
| parentExpand | 54 ms | 2–6 ms |
| **RAG 合计** | **5 870 ms** | **2 338–2 614 ms** |

**被否决的两条路（实测后放弃）**

| 方案 | 实测结果 | 结论 |
|---|---|---|
| int8 动态量化（`torch.ao.quantization.quantize_dynamic`） | 耗时 2616ms → **28 431ms（慢 10 倍）**，分数 0.9987 → 0.4157（模型输出损坏），排序不一致 | **否决**：aarch64 上量化 Linear 走了慢速参考实现 |
| 缩短 `max_length`（512→256） | 3106ms → 2516ms（仅 -19%），且排序轻微变化 | **否决**：收益小、质量有风险 |

### P1-2 检索缓存命中率提升

**问题**：缓存键含完整 query，政策问法措辞差异极大 → 命中率≈0，每轮都付完整 RAG 成本。

**措施**

| 文件 | 改动 |
|---|---|
| `rag/SemanticRetrievalCache.java`（新增） | Redis LIST 存最近 128 条 (问法, 缓存键, 查询向量)；查询时按余弦相似度匹配，阈值 0.92 |
| `rag/RawQueryExtractor.java`（新增） | 从增强后的用户消息中抽出**真实用户问题** |
| `rag/HybridRetrievalPipeline.java` | 缓存键 / 语义注册 / 嵌入**统一使用真实问题** |
| `rag/RetrievalCacheWarmup.java`（新增） | 启动后延迟 20s，后台预热 12 条高频政策问法 |
| `application.yml` | `cache-ttl-minutes` 10 → 30；新增 `semantic-cache-*` / `warmup-*` |

**修掉的一个隐蔽缺陷**：RAG 的 query 来自 `QuestionAnswerAdvisor`，拿到的是被
`ExecutionPromptBuilder` 增强后的**完整提示词**（2000–4000 字符，含【执行要求】等模板）。
直接用它做嵌入有三个后果：
① 模板噪声稀释真实问题的语义向量；② 嵌入耗时随长度线性增长（实测 140ms ↔ 2700ms 剧烈波动）；
③ 语义缓存的向量被模板主导，改写问法的相似度被稀释。

抽出真实问题后，语义缓存登记的问法从 3000 字符的完整提示词变成
`山东省汽车以旧换新补贴政策是什么`（23 字符）。

**实测（6 个同义改写）**

| 检索层结果 | 次数 |
|---|---|
| semanticCacheHit | **4** |
| cacheHit（精确键） | 1 |
| cacheMiss | 1 |

**命中时 RAG 阶段耗时：4 070 ms → 130 ms（-97%）**。
预热实测：12 条问法 548ms 全部写入缓存。

> 注：改写问法未命中时，RAG 会重新执行（2.3–2.6s），但总耗时仍由模型生成主导，
> 所以端到端的收益小于 RAG 阶段的收益。

## 四、实施过程中额外修复的 3 个隐性故障

这些都不是本次优化目标的一部分，但由实测暴露出来，且都直接影响了耗时或可用性。

### 1. Rerank 从未生效（见 P1-1）

`.body(Object.class)` → 解析失败 → 静默降级纯向量。每轮白等 5s。

### 2. 后台摘要与 ReAct 规划器用错了模型 Key → 稳定 401

`RedisChatMemory`（对话摘要）与 `ReActPlanningService`（ReAct 规划）注入的是
Spring 默认的 `ChatModel` Bean，其 Key 固定为 `spring.ai.openai.api-key`（即 `DASHSCOPE_API_KEY`），
**与管理员在管理台配置的模型无关**。管理员改用别的模型后，这两处稳定返回
`401 invalid_api_key`：

```
[chat-async-2] SpringAiRetryAutoConfiguration : Retry error ... HTTP 401 - invalid_api_key
```

后果：会话摘要**从未成功写入**（多轮上下文无法压缩），ReAct 规划器**永远走兜底计划**。

**修复**：抽出 `RuntimeChatModelProvider`，统一解析运行时模型配置，
`RedisChatMemory`（改为 `chatModelSupplier`）与 `ReActPlanningService` 共用。
顺带解决了 P2-3 的连接复用。

### 3. 工具回调解析失败直接 500

模型请求了 MCP 工具 `spring_ai_mcp_client_amap_maps_text_search`，
Spring AI 抛 `IllegalStateException: No ToolCallback found`。
该异常**不是** `ToolExecutionException`，不会被 `ToolFailureConfig` 里的
`ToolExecutionExceptionProcessor` 兜住，一路冒泡成 500。
已由 P2-1 的降级路径覆盖。

## 五、遗留项与后续建议

### 遗留 1：TTFT 仍由模型思考主导（P0-2 按要求保留）

流式 TTFT P50 = 12.3s，而模型「首字可见」的时间几乎全部花在**不可见的思考过程**上。
直连压测（2750 token 的 RAG 规模 prompt）：

| 模式 | 首字可见 TTFT | 总耗时 | completion token |
|---|---|---|---|
| 默认（思考开） | 3 595 / 5 171 ms | 9 366 / 10 679 ms | 602 / 687 |
| `enable_thinking=false` | **547 / 415 ms** | **6 758 / 6 449 ms** | 444 / 454 |

即：若将来允许关闭思考，**TTFT 可从 12.3s 降到约 0.5s**，总耗时再降约 30%。

**实施障碍（已确认）**：Spring AI 1.0.3 的 `OpenAiChatOptions` **没有 `extraBody` 通用字段**
（`javap` 已确认），无法把 `enable_thinking` 透传到百炼的 OpenAI 兼容端点。
可行路径：
1. 换用百炼原生客户端（引入 `spring-ai-starter-model-dashscope`，其 `DashScopeChatOptions` 带 `enableThinking`）；
2. 自建 `OpenAiApi` 请求体扩展 / `RestClient` 拦截器注入 `enable_thinking:false`（需用单测锁定 JSON 结构，防止 Spring AI 升级失效）；
3. 换用该部署上可用的非思考模型 —— 但实测该 Model Studio 部署**只开通了 `qwen3.8-flash` 一个模型**，
   其它模型返回 `403 免费额度耗尽` 或 `404 模型不存在`。

> 另注：本次确认 `deploy/.env` 里替换后的 Tavily Key 已生效，直连 `api.tavily.com` 返回 200 与 3 条结果。

### 遗留 2：completion token 波动主导总耗时（P0-3 按要求保留）

优化后端到端耗时与 completion token 高度相关：

| completion token | 端到端 |
|---|---|
| 607 | 9 549 ms |
| 896 | 19 409 ms |
| 1 780 | 56 938 ms |
| 2 485 | 53 665 ms |
| 3 006 | 58 464 ms |

模型生成速率约 55–70 tok/s，这是当前耗时的唯一主导项。若后续允许限制回答长度
（`max_tokens` + 提示词约束），P95 有望压到 20s 以内。

### 遗留 3：Rerank 仍占 RAG 阶段 90%+

单次 2.2–2.6s（6 条候选、约 2000 字符）。进一步提速的方向：

| 方向 | 预期 | 风险 |
|---|---|---|
| 换更小的重排模型（如 bge-reranker-base，278M vs 568M） | 约 -45% | 重排质量下降，需回归命中率 |
| GPU 部署 reranker | 数倍 | 需要 GPU 环境 |
| 只对向量召回 top-6 重排（跳过关键词召回的候选） | 约 -20% | 牺牲关键词召回的多样性 |

### 遗留 4：检索缓存的正确性边界

语义缓存按查询向量做近似匹配（阈值 0.92）。实测「汽车报废更新」与「汽车置换更新」
是**不同政策**，相似度未达阈值 → 正确地未命中 ✓。但语义相近而答案不同的问题
（如同一年份不同地市的补贴标准）仍需人工复核。可考虑把 `publishYear` / 检索范围
纳入语义索引键，进一步收紧。
