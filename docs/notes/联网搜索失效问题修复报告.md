# 联网搜索失效问题修复报告

> 现象：管理台已打开「联网搜索」开关，问「你联网搜索一下价格，iPhone17标准版256GB」仍搜不到价格，
> 模型回复"根据当前可获取的政策资料，未检索到 iPhone17 标准版 256GB 的可靠实时销售价格"。
>
> 修复日期：2026-11-05　｜　涉及模块：意图路由 / 工具注册 / 工具开关 / 向量缓存

---

## 一、结论速览

不是 Tavily 失效，也不是模型不听话。**联网搜索从头到尾就没有被触发过** —— 搜索结果从未进入模型上下文。

| # | 缺陷 | 性质 | 修复位置 |
|---|------|------|----------|
| **A** | 「iPhone17**标准**版」的"标准"命中政策关键词 → 判为"政策+价格混合问法" → **计划里没有 webSearch 步骤** | **主因** | `QueryIntentRules` / `ReActPlanningService` |
| **B** | 用户显式说"联网搜索"时，仍被"先政策后价格"的保守策略压制 | **主因** | `QueryIntentRules` / `ReActPlanningService` / `ExecutionPromptBuilder` |
| **C** | `webSearch` 从未注册为 ToolCallback，模型的 tools schema 里根本看不到它 | **主因** | 新增 `BuiltinToolCallbackProvider` |
| **D** | 管理台「工具管理」页开关写 `tool_definition.is_enabled`，运行时读 `agent_config.skills.*` → **开关是哑弹** | 缺陷 | `ToolStateManager` |
| **E** | 搜索结果写向量库绑定了失效的 DASHSCOPE Key → 每次 401，该能力从未生效 | 缺陷 | `WebSearchTool` |

**修复效果（同一句用户原话）**：

| | 修复前 | 修复后 |
|---|---|---|
| 模型回复 | "未检索到 iPhone17 标准版 256GB 的可靠实时销售价格" | 给出 5999/5899 元、国补测算、**3 条来源链接** |
| 规划路径 | 政策+价格混合路径（needToolCall=false） | 显式联网请求路径（needToolCall=true） |
| 服务端预执行 | 未触发 | 已触发，返回 3 条结果 |
| 向量库写入 | 401 invalid_api_key | 成功 |

## 二、根因分析

### 2.1 证据链（修复前的真实日志）

```
ReAct 规划命中政策+价格混合路径（先政策后价格） | needToolCall=false
进入智能体执行阶段 | needToolCall=false | enableRag=true | preExecutedTools=false
```

这三个字段同时为 false，直接锁定了断点：

- `needToolCall=false` → 计划里没有外部工具步骤
- `preExecutedTools=false` → 服务端预执行器没有执行 webSearch
- 于是模型上下文里只有 RAG 政策文档 → 只能回答"未检索到"

同时日志里有一条**干扰项**，容易误判为"搜索其实跑了"：

```
执行 Tavily 联网搜索 | 关键词=iphone17 价格 山东 | 结果数=3
```

这条来自**价格预取**（`ProductPriceCacheService`）的独立异步链路，目的是把价格写进 Redis 供后续轮次复用，
**与本次请求的模型上下文无关**。关键词是拼装出来的"iphone17 价格 山东"，
且预取在 `进入智能体执行阶段` 之后才完成（日志时间戳晚于该行）。

真正说明问题的是：**模型这次请求没有产生任何搜索结果**。

### 2.2 缺陷 A：「标准版」被当成政策关键词

`QueryIntentRules.isPolicyPriceMixed()` 原实现：

```java
boolean hasPolicy = containsAny(normalized,
        "政策", "补贴", "国补", "以旧换新", "申领", "流程", "条件", "资格", "标准", "规则");
boolean hasPrice = containsAny(normalized, "价格", "报价", "市场价", "多少钱", "优惠", "到手价", "售价", "价位", "价");
return hasPolicy && hasPrice;
```

用户消息 `你联网搜索一下价格，iphone17标准版256gb`：

- 政策词命中：**「标准」**（来自型号后缀"标准版"）→ `hasPolicy = true`
- 价格词命中：「价格」→ `hasPrice = true`
- → `isPolicyPriceMixed = true`

而 `ReActPlanningService.tryBuildShortcutPlan()` 中，混合问法分支**排在实时查询分支之前**，
一旦命中就返回一个 `needToolCall=false`、只含 RAG 步骤的计划 —— **webSearch 步骤根本没被生成**。

这是整条链路的第一道闸门，后面的预执行、工具注册全都没机会生效。

> 注意「政策关键词」这一组词本身的脆弱性：`标准/条件/流程/资格/规则` 在商品描述里极常见
> （"iPhone17标准版"、"华为的激活条件"…），单独用它们判定政策意图必然产生误判。

### 2.3 缺陷 B：显式联网指令被保守策略压制

即使修好 A，还有一道闸门：`requiresRealtimeSearch()` 与 `enforceRealtimeWebSearch()` 里都有
`if (isPolicyPriceMixedQuestion(...)) return false/plan;` 的短路。

其设计意图是合理的：混合问法下先给政策结论、按需再补价格，避免每次都联网。
但它没有区分**"隐含的价格诉求"**和**"用户明确要求联网"** —— 后者被显式指令覆盖了。

`ExecutionPromptBuilder.buildExecutionPrompt()` 里的【混合问法补充策略】更直接：

```
2. 若暂缺实时价格证据，不要编造最新价格；引导用户补充品牌+型号后再执行 webSearch。
```

模型被明确指示"不要给价格、去让用户补充型号"，于是照做 —— 输出了截图里那段"未检索到…"。

### 2.4 缺陷 C：webSearch 从未注册为 ToolCallback

这是最根本的一处。项目的工具实现形态是：

```java
@Bean
@Description("联网搜索工具…")
public Function<SearchRequest, SearchResponse> webSearch() { ... }
```

而 `DynamicChatClientFactory` 只装配了 MCP 的 `ToolCallbackProvider`：

```java
builder.defaultToolCallbacks(toolCallbackProviders.toArray(ToolCallbackProvider[]::new));
```

Spring AI **不会**把 `Function` 类型的 Bean 自动转成工具（`FunctionToolCallback` 需要显式包装）。
后果有两层：

1. 模型的 tools schema 里**看不到** webSearch —— 它没有任何途径主动发起搜索；
2. 一旦服务端预执行被意图路由跳过（缺陷 A/B），模型就**彻底失去联网能力**，
   只能基于 RAG 政策文档作答 —— 这正是截图里的现象。

修复前项目里 `webSearch` 的唯一调用方是服务端预执行器（`PlannedToolExecutor`），
模型侧完全没有兜底路径。

### 2.5 缺陷 D：管理台开关是哑弹

管理台有两个地方能开关工具，各自写入不同的表：

| 入口 | 写入位置 | 运行时是否读取 |
|------|---------|--------------|
| 智能体页（AgentsTab） | `agent_config.skills.webSearch.enabled` | ✅ 是 |
| **工具管理页（ToolsTab）** | `tool_definition.is_enabled`（code=`web_search`） | ❌ **否** |

`ToolDefinitionService` 是唯一引用 `ToolDefinition` 实体的类，运行时链路完全不看它。
用户「在工具管理页打开联网搜索」这个动作对运行时**零影响** —— 这正是"我明明打开了"却没效果的由来。

### 2.6 缺陷 E：向量缓存 401

```
搜索结果缓存到向量数据库失败 | 关键词=iphone17 价格 山东
org.springframework.ai.retry.NonTransientAiException: HTTP 401 - {"error":{"code":"invalid_api_key"}}
```

`WebSearchTool` 注入的是 `@Qualifier("vectorStore")` —— Spring AI 自动装配的那个，
绑定 `spring.ai.openai.embedding`（固定 `DASHSCOPE_API_KEY`，已失效）。
实际知识库在 `vector_store_ollama_bge_m3_1024`（4036 条），由 `runtimeRagVectorStore` 管理。

实测确认：`vector_store` 表 **0 条**（写入全部失败），`vector_store_ollama_bge_m3_1024` 有 4036 条。
即"搜索结果缓存到向量库"这个能力**从未真正生效过**。

## 三、修复方案

### 3.1 意图路由：强弱政策词分离 + 显式联网请求短路

**`QueryIntentRules`** —— 拆分政策关键词强弱，并新增显式请求判定：

```java
/** 强信号：几乎不可能出现在商品名里 */
public static final Set<String> STRONG_POLICY_KEYWORDS = Set.of("政策","补贴","国补","以旧换新","申领");

/** 弱信号：必须与强信号共现才算政策意图（"标准版/条件/规则"在商品语境极常见） */
public static final Set<String> WEAK_POLICY_KEYWORDS = Set.of("流程","条件","资格","标准","规则");

/** 显式联网请求：用户点名要求联网，优先级最高 */
public static final Set<String> EXPLICIT_SEARCH_KEYWORDS = Set.of(
        "联网搜索","联网查","上网查","上网搜","网上搜","网上查",
        "搜一下","搜索一下","查一下最新","帮我搜","帮我查");

public static boolean isPolicyPriceMixed(String normalized) {
    boolean hasPolicy = containsAny(normalized, STRONG_POLICY_KEYWORDS)
            || (containsAny(normalized, WEAK_POLICY_KEYWORDS)
                && containsAny(normalized, STRONG_POLICY_KEYWORDS));
    ...
}
```

**`ReActPlanningService`** —— 显式联网请求分支置于混合问法分支**之前**，
并在 `requiresRealtimeSearch()` 中放行：

```java
if (isPolicyPriceMixedQuestion(normalized) && !isExplicitSearchRequest(normalized)) {
    return false;   // 仅在"非显式请求"时才被混合问法压制
}
```

**`ExecutionPromptBuilder`** —— 同样的放行逻辑，且显式请求时**不再注入**
"引导用户补充品牌+型号后再执行 webSearch"的保守策略。

### 3.2 工具注册：webSearch / calculateSubsidy 成为模型可见工具

新增 `BuiltinToolCallbackProvider`，用 `FunctionToolCallback` 显式包装两个内置 Function：

```java
FunctionToolCallback.builder("webSearch", webSearchTool.webSearch())
        .description("联网搜索工具…")
        .inputType(WebSearchTool.SearchRequest.class)
        .build();
```

该类实现 `ToolCallbackProvider` 且标注 `@Component`，
Spring 会自动把它与 MCP 的 provider 一起收集进 `ObjectProvider<List<ToolCallbackProvider>>`。

部署后实测装配结果：

```
ChatClient 已装配工具回调 | providers=2
  tools=[webSearch, calculateSubsidy,
         spring_ai_mcp_client_amap_maps_maps_regeocode, … 11 个高德工具]
```

至此形成**双保险**：
- 服务端预执行（原有路径，确定性高，不多花一轮模型往返）
- 模型自主调用（兜底路径，预执行被跳过时模型仍能联网）

### 3.3 工具开关：两套开关同时生效

`ToolStateManager` 新增全局开关查询，与智能体级开关取 AND：

```java
private static final Map<String, String> SKILL_KEY_TO_TOOL_CODE = Map.of(
        "webSearch", "web_search",
        "subsidyCalculator", "subsidy_calculator",
        "fileParser", "file_parser");

public boolean isEnabled(String skillKey) {
    if (!isGloballyEnabled(skillKey)) return false;   // 管理台「工具管理」页
    ... // 原有 skills 判断
}
```

记录不存在 / 查询异常时放行，避免数据库抖动导致工具整体不可用。

### 3.4 向量缓存：改用运行时向量库

```java
// 必须用 runtimeRagVectorStore：auto-configured 的 "vectorStore" 绑定的是
// spring.ai.openai.embedding（固定 DASHSCOPE_API_KEY），该 Key 已失效 → 401
public WebSearchTool(@Qualifier("runtimeRagVectorStore") VectorStore vectorStore, ...)
```

**写入隔离已核实**：搜索结果文档不含 `knowledgeDocumentId` 与 `chunkLevel`，
而检索 SQL 有双重过滤（`JOIN knowledge_documents` + `chunkLevel='child'`），
因此不会污染政策检索。实测政策文档 4036 条不变，web-search 文档独立计数。

### 3.5 搜索关键词清洗

用户常把指令与检索词写在一起（"你联网搜索一下价格，iPhone17标准版256GB"），
原样送进 Tavily 会稀释检索意图。新增 `stripSearchInstruction()` 剥离前缀性指令：

```
修复前关键词： 你联网搜索一下价格，iPhone17标准版256GB
修复后关键词： 价格，iPhone17标准版256GB
```

保留"价格/报价"等描述查询维度的词（对检索电商报价确有帮助）。

## 六、遗留说明

1. **搜索关键词仍包含"价格"字样** —— 清洗只剥离指令前缀，保留查询维度词。
   若追求更纯粹的检索词，可进一步剥离，但需评估"价格"对电商报价召回的贡献。

2. **价格预取与计划内搜索是两套独立机制** —— 前者写 Redis 价格缓存供后续轮次复用，
   后者把结果注入当前模型上下文。二者都会调用 Tavily，存在重复检索的可能。
   当前有 singleflight + Redis 缓存兜底，实测未见明显放大；后续可考虑统一。

3. **MCP 高德工具的 11 个条目全部暴露给模型** —— 这会让每次请求的 tools schema 变大。
   当前 tools schema 长度可接受，但若 MCP 工具继续增加，建议按需裁剪。

4. **`tool_definition` 与 `agent_config.skills` 的双开关语义** —— 现在是 AND 关系，
   任一关闭即禁用。若后续产品上需要"全局开关覆盖智能体级开关"，需再调整语义。
