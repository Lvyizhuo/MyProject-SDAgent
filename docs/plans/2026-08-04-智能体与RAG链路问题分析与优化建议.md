# 智能体链路与 RAG 链路问题分析与优化建议

> 日期：2026-08-04
> 范围：后端核心对话链路（ChatService → ReAct 规划 → 工具调用 → Advisor 链）与 RAG 检索链路（检索 → 重排 → 上下文注入）
> 结论：**主链路与完整检索链路脱节是当前最核心的架构问题；多处规则重复为最大技术债；整体不建议通过换语言（Python 重构）解决，建议按本文 P0-P2 顺序修复**

---

## 一、智能体链路

### 1.1 链路全景

```
ChatService.chat()（1204 行）
├─ 1. SessionFactCacheService.mergeFacts()      结构化多轮事实合并
├─ 2. 商品价格缓存补全（命中直接注入 facts）
├─ 3. 澄清问题判定（缺品类/价格/年份 → 反问）
├─ 4. FastPathService 规则硬编码快速路径（问候/材料/流程…）
├─ 5. QA 语义缓存查询（余弦 0.92）
├─ 6. 纯价格查询 → 异步预取 + 同步阻塞等待（最长 6s）
├─ 7. ReActPlanningService.createPlan()         LLM 规划（快捷规则优先）
├─ 8. ToolIntentClassifier.classify()           规则二次校验工具参数
├─ 9. enforceRealtimeWebSearch()                强时效查询强制改写计划
├─ 10. 计划渲染为执行提示词（计划本身只是 prompt 装饰）
└─ 11. executeChatWithFallback() 多级降级链
     ├─ Spring AI ChatClient（Advisor 链：Security→Memory→ReReading→QA→Logging）
     ├─ 失败 → 关闭 RAG 重试
     ├─ 失败 → 原生 REST 直连降级
     └─ 超时/网络 → 本地兜底文案
```

### 1.2 设计亮点（保留）

- 成本漏斗分层合理：FastPath 规则 → QA 语义缓存 → RAG → 工具调用，逐层降级省钱
- 降级链路完整：Spring AI → 原生 REST → 本地文案，每层有兜底
- `ToolIntentClassifier` 作为"工具调用保险丝"，拦截无效工具调用
- 快捷路径（shortcut plan）覆盖高频场景，避免每次都付一次 LLM 规划调用
- 动态模型路由带三级回退（managed → manual → default）

## 二、RAG 链路

### 2.1 核心发现：两套检索路径脱节

项目内存在**两套检索路径**，用户对话走的是简陋的那套：

```
【完整链路】RagRetrievalService.retrieveRelevantDocuments()  ← 死代码
   同义词扩展 → 向量召回20 + 关键词召回20 → RRF融合 → rerank(→3)
   → 阈值过滤 → parent扩展(±1邻居) → 年份偏好排序
   唯一调用者：RagPrefetchService.prefetch()
   → RagPrefetchService 全代码库无任何调用者
   （RagRetrievalService.java:37 / RagPrefetchService.java:31）

【主链路·实际生效】QuestionAnswerAdvisor → RuntimeRagVectorStore.similaritySearch
   → similaritySearchInFolderScope：纯向量 SQL，topK=3，直接返回
   （MultiVectorStoreService.java:93-119 / SimplePgVectorStore.java:703-720）
```

**后果**：三 provider 重排序（TEI/Xinference/DashScope + 404 自动重试）、混合检索 RRF 融合、parent-child 两级扩展、政策年份偏好排序——**全部未在生产对话链路生效**。生产主链路 = "嵌入一次 query → 取最近 3 条向量"。

### 2.2 问题清单

| # | 优先级 | 问题 | 位置 | 影响 |
|---|--------|------|------|------|
| R1 | **P0** | 主链路未接入完整检索链路（无 rerank、无关键词混合、无 parent 扩展、无年份排序） | `RagRetrievalService.java:37` 仅被 `RagPrefetchService.java:36` 调用，而 `RagPrefetchService` 无调用者 | 召回质量远低于设计预期；重排服务、混合检索投入白费 |
| R2 | **P0** | `similarityThreshold=0.5` 配置在主链路完全失效：folder-scope SQL 与 SimplePgVectorStore 的 SQL 均无阈值 WHERE 条件 | `MultiVectorStoreService.java:113-119`、`703-720` | 与知识库完全无关的问题也会注入 3 条文档，模型可能基于无关内容作答 |
| R3 | **P1** | 两套 VectorStore 体系并存：Spring AI 自动配置 `vector_store` 表（无人消费）+ `RerankingVectorStore`（@Primary，全库无注入者）+ 自研 `SimplePgVectorStore`（每模型独立表，实际使用） | `RerankVectorStoreConfig.java:15-22` | @Primary 是定时炸弹：未来按类型注入 VectorStore 的代码会静默拿到走错误表的包装器 |
| R4 | **P1** | 中文关键词检索（BM25）基本失效：`to_tsvector('simple', …)` 不识别中文分词 | `MultiVectorStoreService.java:173+` | 中文政策文档关键词召回为空集（当前在死代码链路，接入主链路前必须修复） |
| R5 | **P1** | 死代码清理：`RagPrefetchService`、`RerankingVectorStore` 包装器、`retrieveWithFilter`/`retrieveByCategory` 占位实现 | `service/RagPrefetchService.java`、`rag/RerankingVectorStore.java`、`RagRetrievalService.java:107-113` | 误导后续维护者，掩盖真实链路 |
| R6 | **P2** | 入库嵌入逐条串行 + 逐条 INSERT（未用已有批量 embedTexts） | `MultiVectorStoreService.java:657-680` | 大批量文档导入耗时线性增长，可提速 10-20 倍 |
| R7 | **P2** | 检索 SQL 的 metadata jsonb 提取 + CAST 无法走索引；folder path LIKE 前缀匹配 | `MultiVectorStoreService.java:100-119` | 数据量大时全表扫描 |
| R8 | **P2** | 主链路无检索结果级缓存（QA 语义缓存恰好排除了政策/补贴/价格类问题，即 RAG 最常服务的领域） | `ChatService.java:791-799` | 政策类问题每次重复嵌入 + 检索 |
| R9 | **P2** | `RagFailureDetector` 按错误消息字符串匹配（"embedding"、"vector store" 等过泛） | `RagFailureDetector.java:16-29` | LLM 输出文本含这些词时误判 RAG 故障 → 白降级重试一次 |
| R10 | **P2** | prompt 截断为硬截断（substring 1200 字符），政策条款可能在关键数据处被切断 | `RuntimeRagVectorStore.java:161-173` | 模型拿到残句，答案准确性受损 |

## 三、优化建议汇总

| 优先级 | 动作 | 效果 |
|--------|------|------|
| **P0** | 主链路接入 `RagRetrievalService` 完整链路（或把 rerank 逻辑接到 `RuntimeRagVectorStore` 上），同时给 folder-scope SQL 补上阈值 WHERE 条件 | 召回质量质变；配置阈值生效 |
| **P0** | 抽取共享规则引擎（关键词表集中定义），消除 5 处重复；或由 `ToolDefinition` 实体驱动 | 消除最大技术债，判定一致 |
| **P0** | 计划必达：含 calculateSubsidy/webSearch 的计划由服务端先调工具再生成答案 | 工具调用成功率可控 |
| **P1** | 拆分 ChatService（ClarificationService / PricePrefetchCoordinator / ExecutionFallbackChain） | 主链路可读、可测试 |
| **P1** | 删除流式死代码（Controller 410 + ChatService stream 相关） | 单一路径，降低维护成本 |
| **P1** | SecurityAdvisor order 改为负值确保最先执行；敏感词按场景收窄 | 修复记忆注入绕过面、减少误拒 |
| **P1** | 决定两套 VectorStore 去留：删除 @Primary RerankingVectorStore 与 Spring AI `vector_store` 自动配置，或统一到一条链路 | 消除双检索路径隐患 |
| **P1** | 修复中文关键词检索（zhparser/jieba 或退化 LIKE 匹配 + 倒排缓存）后接入 RRF | 混合检索真正可用 |
| **P2** | 价格预取改非阻塞/缩短等待；规划用专用线程池；图片识别并行 | 降低延迟 |
| **P2** | 入库批量嵌入 + 批量 INSERT（batch 32-64） | 导入提速 |
| **P2** | 检索结果级缓存（query hash → 文档 id 列表，5-10min TTL） | 减少重复检索成本 |
| **P2** | RagFailureDetector 改按异常类型判断；截断改按句号/条款边界智能截断 | 减少误降级、避免残句 |

## 四、建议实施顺序

```
第一阶段（P0，预计 2-3 人周）：
  1. 接通主链路到完整检索链路 + 补阈值过滤（R1/R2）—— 召回质量质变
  2. 抽取共享规则引擎（A1）—— 先统一规则，后续拆分才有基础
  3. 计划必达：工具先执行再生成（A2）

第二阶段（P1，预计 2-3 人周）：
  4. 拆分 ChatService + 删除流式死代码（A3/A4）
  5. SecurityAdvisor 顺序与敏感词修复（A5）
  6. VectorStore 体系收敛（R3）+ 中文关键词检索修复（R4）
  7. 清理死代码（R5）

第三阶段（P2，按需排期）：
  8. 性能与成本优化（A6-A12 / R6-R10）
```

> 注：**不建议通过 Python 重构解决上述问题**——问题本质是设计缺陷而非语言缺陷，重构只是翻译；现有 Spring AI 生态（Advisor 管道、工具循环、MCP、降级链）是已打磨好的资产。若未来确需 Python 化，优先"算法端独立 Python 服务"（4-6 人周），后端编排层保留 Java。
