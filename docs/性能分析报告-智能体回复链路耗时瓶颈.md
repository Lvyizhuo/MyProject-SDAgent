# 性能分析报告：智能体回复链路耗时瓶颈

- **分析对象**：山东省智能政策咨询助手（`MyProject-SDAgent`）`POST /api/chat` 完整链路
- **分析日期**：2026-11-04
- **测量环境**：macOS arm64 / Docker Desktop 4.97.0；后端 `eclipse-temurin:21-jre-alpine` 容器；
  模型 `qwen3.8-flash` @ 阿里云百炼 Model Studio（`llm-hzv9kw2g50lpbkw3.cn-beijing.maas.aliyuncs.com`）；
  reranker `BAAI/bge-reranker-v2-m3`（CPU 推理）；嵌入 `ollama:bge-m3`；PostgreSQL 16 + pgvector；Redis 7
- **测量方式**：在链路上插入分阶段计时（`support/StageTimer` + `advisor/TimingAdvisor`），
  以真实后端二进制、真实数据库/缓存/检索链路发起请求，逐阶段采集耗时；
  模型侧另做直连压测（流式 TTFT、思考开关、候选数敏感性）
- **复现脚本**：`scripts/perf/measure-chat-latency.py`

## 一、链路梳理

### 1.1 全链路阶段总览

一次用户提问会依次经过 18 个阶段。其中 **⑭ RAG 检索** 与 **⑮ 模型调用** 是仅有的两个重计算阶段。

| # | 阶段 | 代码位置 | 职责 | 是否调 LLM |
|---|---|---|---|---|
| 0 | 前端发起请求 | `frontend/src/services/api.js:105` → `components/ui/ChatWindow.jsx:188` | 单次阻塞 `fetch`，**无流式** | 否 |
| 1 | 会话创建/落库 | `controller/ChatController.java:63-71` | 会话 upsert + 用户消息入库 | 否 |
| 2 | 会话事实合并 | `service/ChatService.java:84` → `SessionFactCacheService.mergeFacts()` | 从 Redis 读/写会话槽位（价格、品类、区域、年份） | 否 |
| 3 | 价格缓存增强 | `ChatService.java:86` → `PricePrefetchCoordinator.enrichFactsWithProductPriceCacheIfNeeded()` | Redis 查型号价格缓存 | 否 |
| 4 | 价格缓存写入 | `ChatService.java:88` → `cacheProductPriceIfPresent()` | Redis 写 | 否 |
| 5 | 用户消息构建 | `ChatService.java:91` → `buildUserMessage()` | 拼接城市/定位/会话摘要；**含图片时调视觉模型** | 条件 |
| 6 | 澄清判定 | `ChatService.java:94` → `ClarificationService.resolveClarificationStep()` | 纯关键词+槽位规则 | 否 |
| 7 | 快速通道 | `ChatService.java:104` → `FastPathService.tryDirectAnswer()` | 纯规则，命中直接返回硬编码文案 | 否 |
| 8 | 问答语义缓存 | `ChatService.java:118` → `QuestionSemanticCacheService.lookup()` | Redis 精确查 → 未命中则 **调 Ollama 嵌入** → 遍历桶内候选 | 否（嵌入） |
| 9 | 价格预取 | `ChatService.java:132` → `PricePrefetchCoordinator.handlePurePriceQuery()` | 后台 Tavily 预取 + **主线程最多阻塞 1s** 轮询 | 否 |
| 10 | ReAct 规划 | `ChatService.java:136` → `agent/ReActPlanningService.createPlan()` | 规则捷径命中则不调模型；否则 **调模型 1 轮** 输出 JSON 计划 | **是（条件）** |
| 11 | 意图分类 | `ChatService.java:138` → `agent/ToolIntentClassifier.classify()` | 纯规则，判断是否允许调工具 | 否 |
| 12 | 工具预执行 | `ChatService.java:148` → `agent/PlannedToolExecutor.execute()` | 补贴计算（纯计算）+ webSearch（Tavily），**串行** | 否 |
| 13 | 执行提示词构建 | `ChatService.java:159` → `service/ExecutionPromptBuilder.buildExecutionPrompt()` | 组装系统提示 + RAG 上下文 + 工具结果 | 否 |
| 14 | 客户端构建 | `service/ExecutionFallbackChain.java:91` → `DynamicChatClientFactory.create()` | 查 DB 解析模型 + 解密 Key + **新建 `OpenAiApi`/`ChatClient`** | 否 |
| 15 | **RAG 检索** | `advisor/QuestionAnswerAdvisor` → `rag/RuntimeRagVectorStore` → `rag/HybridRetrievalPipeline.retrieve()` | 缓存查 → 向量召回 → 关键词召回 → RRF → **rerank** → 阈值 → parent 扩展 | 否（嵌入+重排） |
| 16 | **模型调用** | `ExecutionFallbackChain.executePrompt()` → `ChatClient.call()` | 主生成；工具回调会触发**多轮** | **是** |
| 17 | 引用构建 | `service/KnowledgeReferenceService.buildReferences()` | 2 次 JPA + 每条引用 1 次 `tableExists` + 1 次 SELECT（N+1） | 否 |
| 18 | 助手消息落库 | `ChatController.java:82` | 写入会话 | 否 |

### 1.2 Advisor 链（阶段 15/16 内部）

`DynamicChatClientFactory.create()` 组装的执行链（`config/ChatClientConfig.java`）：

```
SecurityAdvisor(order=10)      纯词表+正则注入检测，扫描全部历史 UserMessage
  → MessageChatMemoryAdvisor    Redis 取历史（2 次 GET）+ 回写（1 GET + 1 SET）
  → ReReadingAdvisor(order=50) 仅改写 prompt 文本，不额外调模型
  → QuestionAnswerAdvisor       RAG 检索（阶段 15）
  → TimingAdvisor(order=85)     ★本次新增：切分「前置开销」与「模型调用」
  → LoggingAdvisor(order=90)    记录 token 用量与检索结果
  → 模型调用                    （阶段 16）
```

`RedisChatMemory` 参数（`config/ChatClientConfig.java:36-58`）：`maxMessages=8`、`maxMessageChars=1500`、
`summaryTriggerMessages=6`（**第 6 条消息起触发一次后台 LLM 摘要**）、`summaryMaxChars=1200`。

### 1.3 模型调用轮数

一次用户提问的模型调用轮次：

| 场景 | 轮数 | 依据 |
|---|---|---|
| 规则捷径命中（问候/补贴计算/政策检索） | **1 轮**（仅主生成） | 日志 `ReAct 规划命中XX快捷路径` |
| 规划器未命中捷径 | **2 轮**（规划 1 + 主生成 1） | 日志 `ReAct 规划完成` |
| 主生成中模型请求工具 | **2+ 轮**（Spring AI 工具回调循环，每轮一次模型调用） | 实测捕获到 `No ToolCallback found` 异常即发生在第 2 轮 |
| 会话消息数 ≥ 6 | 额外 **1 轮**（后台摘要，不阻塞主链路） | `RedisChatMemory.triggerSummaryIfNeeded()` |

## 二、实测耗时分布

### 2.1 端到端与阶段分解

> 全部为真实后端容器实测，单位 ms。「其他」= 总耗时 − 模型调用 − RAG。

| 场景 | 端到端 | 模型调用 | 占比 | RAG | 占比 | 其他 | prompt tok | completion tok |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| 政策问答（RAG 缓存命中） | 32 499 | 32 341 | **99.8%** | 36 | 0.1% | ~0 | 4 769 | 2 236 |
| 补贴计算（无 RAG） | 18 323 | 18 305 | **100%** | 4 | 0% | ~0 | 971 | 1 003 |
| 申领条件（RAG 缓存未命中） | 28 938 | 23 035 | **79.6%** | 5 870 | **20.3%** | ~0 | 4 919 | 1 307 |
| 多轮第 1 轮 | **87 989** | 82 195 | **93.4%** | 5 777 | 6.6% | ~0 | 4 769 | **3 915** |
| 多轮第 2 轮 | 22 932 | 17 221 | 75.2% | 5 672 | **24.8%** | ~0 | 6 221 | 940 |
| 多轮第 3 轮 | 19 145 | 13 492 | 70.5% | 5 617 | **29.4%** | ~0 | 6 759 | 686 |
| 多轮第 4 轮 | 27 189 | 21 156 | 78.6% | 5 738 | 21.3% | ~0 | 7 179 | 1 020 |
| 问候语（FastPath 命中） | **11** | — | — | — | — | — | — | — |
| 澄清分支 | 1 – 9 | — | — | — | — | — | — | — |

**结论 1：模型调用占端到端耗时的 70%–100%，是唯一的主导项。**

### 2.2 非模型阶段的耗时（全部实测）

`[chat]` 作用域各阶段（单位 ms，取多轮实测典型值）：

```
facts=0~12   priceEnrich=0~3   priceCache=0   buildUserMessage=0   clarification=0
fastPath=0   qaCacheLookup=0~257   pricePrefetch=0   planning=0   intentClassify=0
toolExec=0   buildExecPrompt=0   modelCall=18311~87989
```
`[agentChain]` 作用域：
```
clientCreate=2~3   preModel=4~5870   llmCall=13492~82195   buildReferences=0~34
```

**结论 2：除 RAG 与模型调用外，全链路所有阶段合计 ≤ 300 ms，占比 < 1.5%。**
Redis 会话事实、规则型澄清/意图/快速通道、提示词构建、引用构建**都不是瓶颈**，
优化它们对总时延无感知收益。

### 2.3 RAG 检索管线分解（缓存未命中，5 858 ms）

```
rerank         5023 ms  85.7%   ← bge-reranker-v2-m3 CPU 交叉编码
vectorRecall    624 ms  10.7%   ← Ollama 嵌入 + pgvector HNSW
keywordRecall    87 ms   1.5%   ← pgvector 关键词召回
parentExpand     54 ms   0.9%
cachePut         30 ms   0.5%
yearSort         11 ms   0.2%
rrfFuse           1 ms   0.0%
thresholdFilter   2 ms   0.0%
```

**reranker 候选数敏感性（CPU 实测，约 290 ms/候选，近似线性）**：

| 候选数 | 耗时 | 说明 |
|---:|---:|---|
| 5 | 1 461 ms | |
| 10 | 3 417 ms | |
| **20** | **5 806 ms** | **当前 `candidate-top-k: 20`** |
| 30 | 9 847 ms | |

**结论 3：RAG 耗时几乎全部是 rerank，且随候选数线性增长。**
`RetrievalResultCache`（10 分钟 TTL）命中时 RAG 仅需 2 ms，未命中则固定 ~5.7 s。
生产环境不同 query 命中率极低，等于每轮都要付 5.7 s。

### 2.4 模型侧直连压测

**输出速率**：同步调用 48–87 tok/s。

**关键发现 —— 模型默认开启「思考」，推理 token 对用户不可见**：

| 场景 | prompt tok | completion tok | 可见字符 | 推理块数 |
|---|---:|---:|---:|---:|
| 默认（思考开） | 70 | 1 508 | 798 | 266（不可见） |
| `enable_thinking=false` | 34 | 1 021 | 1 546 | 0 |

completion token 是可见字符的 2–3 倍，多出来的部分全部是用户看不到的推理链。

**流式 TTFT（2750 token 的 RAG 规模 prompt）**：

| 模式 | 首字可见 TTFT | 总耗时 | completion tok |
|---|---:|---:|---:|
| 默认（思考开） | 3 595 / 5 171 ms | 9 366 / 10 679 ms | 602 / 687 |
| `enable_thinking=false` | **547 / 415 ms** | **6 758 / 6 449 ms** | 444 / 454 |

**结论 4：思考开关同时影响总耗时（-30%）与首字延迟（-90%）。**

### 2.5 上下文构造（prompt 构成）

| 组成 | token 量 | 来源 |
|---|---:|---|
| RAG 检索上下文 | ~4 000–4 700 | `top-k=3` × parent 扩展半径 1 → 最多 9 个 chunk × 900 字 |
| 系统提示词 + 用户问题 + 工具结果 | ~70–200 | `agent_config.system_prompt` |
| 会话历史 | 每轮 +600（4 轮累计 +2 410） | `RedisChatMemory`，8 条 × 1500 字 |

实测多轮 prompt token：**4 769 → 6 221 → 6 759 → 7 179**。
单轮场景下，**RAG 上下文占 prompt 的 98%**。

### 2.6 附带发现的两个故障（非耗时问题，但同链路）

1. **Tavily Key 失效导致整轮 500**：`WebSearchTool` 调 `api.tavily.com` 返回 `invalid_api_key`，
   Spring AI 重试后异常上抛，`GlobalExceptionHandler` 返回 500。
   `ExecutionFallbackChain` 的降级链只覆盖「超时/网络异常/404」，**不覆盖工具侧的 401/403**。
2. **MCP 工具未绑定导致 500**：模型请求 `spring_ai_mcp_client_amap_maps_text_search`，
   抛出 `No ToolCallback found for tool name`，同样直接 500。
   工具列表里出现了模型，但执行期找不到回调。

## 三、瓶颈结论

按「耗时占比 × 改造可行性」排序：

| 排名 | 瓶颈 | 实测占比 | 根因 |
|---|---|---|---|
| **1** | **模型生成 + 隐藏思考** | 70%–100% | ① 默认开启思考，推理 token 占 completion 的 50%–65% 且不可见；② 无流式，19–88 s 内屏幕零输出；③ 回答过长（completion 1 003–3 915 token） |
| **2** | **RAG rerank** | 6.6%–29.4% | CPU 跑 bge-reranker-v2-m3 交叉编码，~290 ms/候选 × 20 候选 = 5.8 s；`RetrievalResultCache` 生产命中率≈0 |
| **3** | **上下文膨胀** | 抬升阶段 1 的成本 | topK=3 + parent 扩展半径 1 → 单轮 4 700 token；历史每轮 +600 token 且无上限累积 |
| **4** | **流式缺失（感知延迟）** | 不体现在耗时上，但影响全部体验 | `POST /api/chat/stream` 已下线返回 410；前端 `ChatWindow.jsx:100-108` 每 1.8 s 轮播**假状态文案**，与后端真实阶段无对应关系 |
| **5** | 每请求重建 HTTP 客户端 | 40–60 ms | `DynamicChatClientFactory.create()` 每次 new `OpenAiApi` → 新连接池 → 每次 TLS 握手（实测 40 ms） |
| **6** | 工具侧无优雅降级 | 失败即 500 | 401/403 与「工具未绑定」不在降级链覆盖范围 |

> **第 5、6 项优先级低于前四项，因为它们合计影响 < 2% 的耗时或只在异常路径出现。**
> 但第 5 项是**结构性隐患**：连接池不复用意味着高并发下会耗尽文件描述符并放大 TLS 开销。

## 四、优化方案（分优先级）

### P0 — 感知延迟与总耗时双降（预期 端到端 -30%~-45%，首字延迟 -90%）

#### P0-1 恢复 SSE 流式 + 前端渐进渲染

| 项 | 内容 |
|---|---|
| **改动模块** | 后端 `controller/ChatController`（恢复 `/stream`）、`service/ExecutionFallbackChain.executePrompt`（改 `ChatClient` 流式）、`advisor/LoggingAdvisor`（已有 `adviseStream` 实现）；前端 `services/api.js`、`components/ui/ChatWindow.jsx` |
| **方案** | `ChatController.chatStream` 去掉 410 分支，改用 `chatClient.prompt().stream().chatResponse()` 逐块 `SSEventEmitter` 推送；前端用 `fetch` + `ReadableStream` 解析 `text/event-stream`，逐块渲染到同一条 assistant 消息 |
| **预期收益** | 感知延迟从 **19–88 s → 0.4–0.5 s**（流式 TTFT 实测）。总耗时不变，但用户不再面对空白等待 |
| **风险** | 中。① 需处理客户端断连（`SseEmitter.onCompletion` / `onError` 释放资源）；② 工具回调与 RAG 在流式下的 Advisor 链行为需回归验证；③ `RedisChatMemory` 的 `after` 回调在流式下写入时机需确认；④ 前端需处理 Markdown 增量渲染（`marked` 需对半截 Markdown 容错） |
| **验证** | 用 `scripts/perf/measure-chat-latency.py` 记录 `ttft`（新增指标）；前端 DevTools 观察 SSE 分块到达间隔；连续 20 次长回答场景，确认无内存泄漏与消息重复 |

#### P0-2 关闭模型思考（`enable_thinking=false`）

| 项 | 内容 |
|---|---|
| **改动模块** | `service/DynamicChatClientFactory.create()`（构造 `OpenAiChatOptions` 处） |
| **方案** | 三选一：① **零代码**——在管理台把 `model_provider.model_name` 换成本部署已开通的非思考模型（实测该 Model Studio 部署仅 `qwen3.8-flash` 一个模型，故此路当前不可行）；② 改用 Spring AI 的 `DashScopeChatOptions.enableThinking(false)`（需引入 `spring-ai-starter-model-dashscope`，改动较大）；③ **自建 `OpenAiApi` 请求体扩展**——Spring AI 1.0.3 的 `OpenAiChatOptions` **无 `extraBody` 通用字段**（已用 `javap` 确认），需子类化 `OpenAiApi.ChatCompletionRequest` 或用 `RestClient` 拦截器注入 `enable_thinking:false` |
| **预期收益** | 总耗时 **-30%**（19.2 s → 13.1 s）；首字延迟 **-90%**（10.2 s → 0.4 s）；completion token **-35%**；且可见回答字数反而更多（798 → 1 546 字符） |
| **风险** | 中。思考模式对复杂推理题可能有质量收益，需按题型 A/B 对比准确率；④ 方案 ③ 改动 Spring AI 内部请求构造，升级 Spring AI 版本会失效（建议封装为独立 `DashScopeExtraBodyInterceptor` 并加单测锁定 JSON 结构） |
| **验证** | 直连压测脚本对比 `enable_thinking` 开关下的 completion token、TTFT、总耗时；用 20 条政策题做答案准确率人工/LLM 评审对照 |

#### P0-3 约束回答长度

| 项 | 内容 |
|---|---|
| **改动模块** | `DynamicChatClientFactory.create()`（`optionsBuilder.maxTokens`）、`agent/DefaultAgentConfigLoader` + `agent_config.system_prompt`（提示词约束） |
| **方案** | ① 在 `model_provider.max_tokens` 设为 800–1200（实测该字段已正确映射到 `OpenAiChatOptions.maxTokens`，且 `DynamicChatClientFactory.java:124` 已传递）；② 系统提示词中显式要求「先给结论表格，再补充说明；控制在 N 字以内」 |
| **预期收益** | completion token 从 1 003–3 915 压到 ~800，**总耗时 -40%~-55%**（按 60 tok/s 折算，3 915 token ≈ 82 s → 800 token ≈ 13 s） |
| **风险** | 低–中。截断会丢失长尾内容，需确认前端能优雅处理截断（提示「已截断，请追问细节」）；注意 `max_tokens` **不约束思考 token**，需与 P0-2 配合才有效 |
| **验证** | 对比 3 档 `max_tokens`（500/800/1200）的完整率与耗时；检查历史回复是否出现半句截断 |

### P1 — 后端计算量削减（预期 端到端 -15%~-25%）

#### P1-1 Rerank 提速（单项 -2~4 s）

| 项 | 内容 |
|---|---|
| **改动模块** | `application.yml` `app.rag.retrieval.candidate-top-k`；`rerank-service/server.py`（`CrossEncoder` 推理参数） |
| **方案** | ① `candidate-top-k` 20 → 10（实测 5 806 → 3 417 ms，**-2.4 s**）；② `CrossEncoder(..., max_length=512)` 截断输入（当前 chunk 900 字 ≈ 640 token，超出 bge-m3 的 8192 上限不多但 CPU 耗时与序列长度成正比）；③ 量化（ONNX int8 / torch.quantization）——改动大，放最后评估；④ **把 rerank 与关键词召回并行**（`HybridRetrievalPipeline.executePipeline` 中二者无依赖） |
| **预期收益** | ② ④ 实现成本低：并行化可直接省掉 `keywordRecall` 的 87 ms；① 省 2.4 s（占端到端 8%–13%） |
| **风险** | 低。候选数下调会降低召回质量，需用 30 条真实问题对比 top-3 文档命中率；reranker 量化需重新验证分数分布（阈值 `resolveRerankScoreThreshold` 依赖 rerankScore） |
| **验证** | `scripts/perf/measure-chat-latency.py` 的 `rerank` 阶段耗时 + 检索结果命中率回归集 |

#### P1-2 提升检索缓存命中率（单项 -5.7 s，条件命中时）

| 项 | 内容 |
|---|---|
| **改动模块** | `rag/RetrievalResultCache.java`、`rag/HybridRetrievalPipeline.java:106-117` |
| **方案** | ① 当前缓存键含完整 query，措辞不同即失效 → 改为**语义化缓存键**（query 嵌入向量聚类/最近邻，参考 `QuestionSemanticCacheService` 的做法）；② TTL 10 → 30 分钟；③ 对「政策标准类」高频问题做**预热**（启动时后台填充） |
| **预期收益** | 命中率从≈0 提升到 30%–50% 时，RAG 阶段从 5 858 ms 降到 2–3.8 s，平均 **-2~-4 s** |
| **风险** | 中。语义化缓存可能命中语义相近但答案不同的问题（政策有年份差异），必须把 `publishYear`/检索范围纳入键，并设置相似度下限（参考 `QuestionSemanticCacheService` 的 `semantic-threshold: 0.92`） |
| **验证** | 构造 50 组改写问法，统计命中率与答案一致性；`RetrievalResultCache` 加命中率埋点 |

#### P1-3 上下文瘦身（单轮 prompt -30%~-50%）

| 项 | 内容 |
|---|---|
| **改动模块** | `application.yml` `app.rag.retrieval.top-k` / `candidate-top-k`；`rag/HybridRetrievalPipeline.expandParentWithNeighbors()` 的 `PARENT_EXPAND_RADIUS`；`config/ChatClientConfig.java:46-48` 的 `maxMessages`/`maxMessageChars` |
| **方案** | ① `top-k` 3 → 2（-33% 检索文本）；② `PARENT_EXPEND_RADIUS` 1 → 0（parent 扩展是当前 4 700 token 的主因：3 篇 × 3 chunk = 9 段，降为 3 段）；③ `maxMessages` 8 → 6、`maxMessageChars` 1500 → 1000（多轮累计 -40%）；④ 历史超长时只保留最近 2 轮原文 + 1 条结构化摘要 |
| **预期收益** | prompt 4 769 → ~2 500，prefill 与首字延迟同步下降；配合 P0-2 后总耗时再降 10%–20% |
| **风险** | 中。裁剪会削弱多轮上下文与答案引用完整性（`references` 的 `snippet` 依赖原文），需回归多轮追问场景 |
| **验证** | 同一批 30 条政策题的引用完整率、答案准确率回归；对比 prompt token 分布 |

### P2 — 健壮性与结构优化（不影响主耗时，但降低风险）

| 编号 | 问题 | 改动位置 | 说明 | 优先级理由 |
|---|---|---|---|---|
| P2-1 | **工具失败不降级**，401/403 与「工具未绑定」直接 500 | `service/ExecutionFallbackChain.fallbackForSyncChatFailure` / `shouldUseDirectRestFallback` | 现有降级只认「超时/网络异常/404」；应扩展为「任意工具侧异常 → 跳过该工具、让模型基于已有上下文作答」 | 异常路径，收益不在时延，但直接影响可用性 |

| P2-5 | **前端无超时/取消** | `frontend/src/services/api.js:105` | 加 `AbortController` + 60 s 超时；用户可中途取消，省后端算力 | 低 |
